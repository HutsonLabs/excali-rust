Upstream renders by calling `CanvasRenderingContext2D` directly (`packages/element/src/renderElement.ts`, `packages/excalidraw/renderer/staticScene.ts`). The port splits that at one type, `excali_scene::display::DisplayList` ([ADR-008](../../decisions/adr-008-crate-boundaries/)): `excali-scene` turns elements into a list of draws, and the backends turn the list into pixels or markup without knowing what an element is.

| Backend | Crate | Consumes the list through |
|---|---|---|
| Browser canvas | `excali-canvas2d` | `paint(list, ctx)` over the `Context2d` trait; `WebCanvas` forwards to `web-sys` |
| Native pixels (PNG, CLI) | `excali-raster` | `render(list, pixmap, images, text)` into a tiny-skia `Pixmap`; `export_png(document, images, text)` encodes a `display::CanvasDocument` as a PNG (ex-405) |
| SVG | `excali-svg` | `export_to_svg(document, fonts)` writes the `display::SvgDocument`: the document around the drawing (ex-406) and the drawing, `display::SvgNode` trees (ex-407) |

An SVG export also has a document around the drawing: its size, the embedded scene, a clip path per frame, the font faces to inline, and the background. `excali_scene::export::svg_document` computes it from the elements as upstream's `exportToSvg` does, as `display::SvgDocument`, plain data with no element in it. The drawing itself is not a list of draws: upstream's `renderSceneToSvg` builds markup whose structure matters (a group per element, a `<text>` per line, a `<symbol>` per image file, a `<mask>` per arrow label), so `excali_scene::svg_scene` hands the SVG backend that structure as `display::SvgNode` trees, tags with their attributes in upstream's order and values (`display::SvgValue`: text, a number, rough.js path data) the backend prints. `excali-svg` writes it all without seeing an element ([rendering fidelity](../rendering-fidelity/#export-structure)). A PNG export's is `display::CanvasDocument`: the canvas's size in device pixels, the list drawn on it, and the embedded scene as a `display::PngPayload` (`excali_scene::canvas_export`, [rendering fidelity](../rendering-fidelity/#png-export)).

The raster and canvas backends have a `no_element_knowledge` test: `cargo metadata --format-version 1 --no-deps` must show `excali-scene` as their only workspace dependency (by package name, so a renamed dependency such as `ec = { package = "excali-core", .. }` counts as `excali-core`; `the_dependency_check_sees_renamed_packages` pins that on a throwaway workspace). For `excali-canvas2d` that covers normal, dev, build and target-specific dependencies; for `excali-raster` it covers its normal dependencies on every target, and the whole list is fixed at `excali-core`, `excali-scene` and `excali-text`, because its PNG export tests and `png_export` example build their documents from elements through `excali_scene::canvas_export` as its callers do. The library may reach `excali-scene` only through `excali_scene::display`, and no identifier in their code may contain `Element` (comments aside), with `HtmlImageElement`, the browser image type `WebCanvas` draws from, the one allowed name. `excali-svg`'s `no_element_knowledge` holds its library to the same rules with no exception, with `excali-scene` as its only normal dependency; its tests also depend on `excali-core` and `excali-rough`, because they build scenes from elements through `excali_scene::export` as the writer's callers do. `excali-scene`'s `display_module_does_not_know_elements` holds the `display` module to the same identifier rule and to `excali_core::color` and `excali_core::json` as its only paths into `excali-core`, with no path out of `display` into the rest of the crate: a `super` inside a use group (`super::{super::x}`), a `super`, `self` or `crate` after `::` and a renamed `self`, `super` or `crate` are rejected along with `super::super` and `crate::` anything but `display`.

## Items

`DisplayItem` has one variant per kind of canvas draw upstream makes:

| Item | Canvas calls it stands for |
|---|---|
| `Fill { path, color, rule }` | `fillStyle`, the path, `fill(rule)` |
| `FillRect { rect, color }` | `fillStyle`, `fillRect(x, y, w, h)` |
| `Stroke { path, stroke }` | `strokeStyle`, `lineWidth`, `lineCap`, `lineJoin`, `miterLimit`, `setLineDash`, `lineDashOffset`, the path, `stroke()` |
| `Image(ImageItem)` | `imageSmoothingEnabled`, `filter`, `drawImage(img, sx, sy, sw, sh, dx, dy, dw, dh)` |
| `Text(TextRun)` | `font`, `fillStyle`, `textAlign`, `direction`, `fillText(text, x, y)` |
| `Group { transform, opacity, clip, items }` | `save()`, `transform(…)`, `globalAlpha *= opacity`, the clip path and `clip(rule)`, the children, `restore()` |

A `Path` is the list of `moveTo`, `lineTo`, `quadraticCurveTo`, `bezierCurveTo`, `arc` and `closePath` calls, with `Path::rect` and `Path::round_rect` building what the canvas methods of those names build and `Path::from_svg_path_data` what `new Path2D(d)` builds (the SVG path grammar as Chrome reads it, up to the first error; upstream fills freedraw outlines this way). Images are named by id (upstream's `fileId`) and each backend resolves ids in its own store, except the built-in images (`excali_scene::display::BuiltinImage`, ids `excalidraw:…`, resolved by `display::builtin_image_by_id`: upstream's two image placeholders and two link icons, the SVG documents upstream loads from data URLs and draws with `drawImage`), which every backend has. `FillRect` is upstream's `fillRect`, kept apart from a filled rectangular path because the canvas draws it as a rectangle (Skia's `drawRect`), whose edges land to 1/256 of a pixel where a path's snap to quarter pixels. Colours are CSS strings kept verbatim: upstream assigns `element.strokeColor` and `backgroundColor` to `fillStyle`/`strokeStyle` as stored (`applyDarkModeFilter` returns them unchanged unless the theme is dark), so the Canvas 2D backend assigns the same string and the SVG writer prints it as the element stores it.

`excali_scene::rough_canvas::draw` turns a roughjs `Drawable` into items exactly as roughjs 4.6.4's `RoughCanvas.draw` (`bin/canvas.js`) paints it: `path` sets become strokes in the stroke colour, `fillPath` sets fills (`evenodd` for `curve`, `polygon` and `path` shapes), `fillSketch` sets strokes in the fill colour at `fillWeight`, with the stroke and fill dashes and `fixedDecimalPlaceDigits` rounding.

## Semantics

The list means what the same calls mean on a canvas, so the Canvas 2D backend transliterates it and the others reproduce it.

- **Order.** Items paint in list order, source-over.
- **Transforms** compose as `ctx.transform`: a group's matrix applies to its children before the parent's. A matrix with an infinite or NaN entry is ignored as a whole. The canvas ignores only the one call with the bad argument, and upstream positions an element with two calls, `translate(cx, cy)` then `rotate(angle)`, so an element with a NaN angle draws translated and unrotated. A single group of `translate × rotate(NaN)` would lose the translation as well, so producers emit one group per canvas call (the translation's group holding the rotation's) or leave out only the non-finite factor.
- **Opacity** is `globalAlpha`: multiplied through nested groups and applied to each draw on its own, so overlapping draws in one element compound (upstream's multi-stroke rough lines darken where they cross). A product outside `0..=1` is ignored.
- **Clips** are in the group's space after its transform, intersect the enclosing clips and end with the group. An empty clip path hides everything.
- **Colours** are parsed as the canvas parses a `fillStyle` assignment. The Canvas 2D backend leaves that to the browser; for the others `Color::rgba` is a CSS Color 4 parser (named, system and hex colours, `rgb`/`rgba`/`hsl`/`hsla` in both syntaxes, `hwb`, `lab`, `lch`, `oklab`, `oklch`, `color()` in the predefined spaces clipped to sRGB, `none`, `calc()`, `min()`, `max()` and `clamp()`), checked case by case against headless Chrome (`scripts/fixtures/css-color-goldens.sh`, `crates/excali-scene/tests/fixtures/css-colors.json`). So `rgb(255 0 0 / 50%)` is half-transparent red, and `ff0000` or `hsv(0,100%,100%)` are not colours. Not covered: CSS Color 5's `color-mix()` and relative colours, and math functions other than `calc()`, `min()`, `max()` and `clamp()` (`round()`, `mod()`, ...). An assignment the canvas ignores (`""`, `none`, `blue-ish`, which restore keeps as stored) leaves the current style, so the draw paints in it: black on a fresh context (upstream draws each element on a fresh element canvas inside `save()`/`restore()`), or the base state's `fill_style`/`stroke_style`.
- **Canvas value rules**: an odd dash list repeats, a dash list with a negative or non-finite entry or a zero total draws solid, a line width or miter limit of 0 or less draws the default (1, 10), a path command with a non-finite argument is dropped (`rect()` adds nothing at all), a drawing command with no subpath starts one, and an arc adds a line from the current point to its start. An arc's sweep is Chrome's (Blink's `AdjustEndAngle`): the whole circle when the angles are 2π or more apart in the arc's direction or differ but meet modulo 2π going that way (`arc(x, y, r, 0, 2π, true)` is a circle), none when they are equal.
- **Images**: the source rectangle defaults to the whole bitmap, is clipped to it with the destination clipped in proportion, and the dark-theme filter is `invert(93%) hue-rotate(180deg)` (upstream's numeric version for backends without CSS filters). An SVG image is drawn as vector content at the draw's resolution, clipped to the destination; with `globalAlpha` or a filter it is drawn in a layer the filter and alpha then apply to, as Blink's `SVGImage::DrawForContainer` does.
- **Text**: one run per line, `y` on the alphabetic baseline, `x` placed by `textAlign`.

## The Painter contract

`DisplayList::replay(&mut impl Painter)` walks the tree once for every backend. A `Painter` receives each draw with its absolute matrix, alpha and current styles (`PaintState`), the item's colour string and that colour resolved to `Rgba` (the current style when the canvas would ignore it), and receives clips as a `push_clip`/`pop_clip` stack. `replay_from` starts from a base state, such as the device-pixel-ratio scale upstream's `bootstrapCanvas` applies (`renderer/helpers.ts:73-127`). That scale is all `bootstrapCanvas` contributes: it paints the background inside `save()`/`restore()`, so no `fillStyle` survives it, and its `COLOR_WHITE` seed (an invalid background paints white) covers only the background rectangle, which the producer emits. A base `fill_style`/`stroke_style` is for a caller whose context already holds styles.

The Canvas 2D backend isolates each draw in `save()`/`restore()` with `setTransform` and `globalAlpha` set first, assigns the colour string as given so the browser parses it, and pushes a clip as `save()`, `setTransform`, the path, `clip(rule)`. `paint` and `paint_scaled` expect a fresh context; `paint_from` first sets the base state's styles. `WebCanvas::new` loads the built-in images from their SVG data URLs. The raster backend computes each draw's coverage as Chrome's Skia does and composites it through tiny-skia (below), keeps clips as intersected coverage masks, draws images through a pattern shader (sampled as Chrome samples, below), and hands text to a `TextRasterizer` the caller provides from the font pipeline.

## Image files (ex-404)

`excali_raster::decode` turns a scene's `files` into the backend's image store (`ImageFiles`) as `img.src = dataURL` does in the browser (`loadHTMLImageElement`, `packages/element/src/image.ts:21-32`): the data URL is read by the Fetch standard's `data:` URL processor (forgiving base64, percent-decoding), raster formats are recognised from their bytes as Chrome sniffs them (PNG, JPEG, GIF's first frame, WebP, BMP and ICO, through the `image` crate, with the Exif orientation applied as `image-orientation: from-image` does), SVG is read by usvg only when the type is `image/svg+xml`, and a file whose `mimeType` is `application/octet-stream` never loads (`image.ts:57-59`). A file that fails to load has no image, and the scene draws the placeholder for it, as upstream's cache keeps the failed load's promise. Not decoded: AVIF (the `image` crate decodes it only through the C library dav1d) and colour profiles (an ICC profile or PNG `gAMA` is ignored and the pixels taken as sRGB). An SVG image's text needs faces in `svg_options().fontdb`, and its `<image>` elements load from data URLs only, as an SVG in an `<img>` fetches nothing.

`excali_scene::render_element::render_element`, the function `render_static_scene` draws every element with, draws an image element from the render config's image cache (`StaticCanvasRenderConfig::image_cache`: a file id with its MIME type once its image has loaded; a file still loading or failed has no entry). `crates/excali-scene/tests/image_elements.rs` holds it to upstream's own `renderElement` exporting image elements, recorded call by call under jsdom (`tools/goldens/image-elements.mjs`): the placeholder box (`#E7E7E7` or `#2E2E2E`, `fillRect`) and icon (`min(min(w, h) * 0.4, 100)`, never above `min(w, h)`, the error icon for status `"error"`), the crop as the source rectangle, `scale` after the rotation, the rounded clip of `getCornerRadius(min(w, h))`, and `DARK_THEME_FILTER` for SVG files in the dark theme only. Every `fillRect` upstream makes on the static canvas (`bootstrapCanvas`'s background, the placeholder box, the link icon's background) is a `FillRect`, and `tools/goldens/static-scene.mjs` records `fillRect` apart from path fills so `tests/static_scene.rs` holds the port to it.

## The raster backend and Chrome's pixels

Upstream draws with Chrome's canvas, so `excali-raster` reproduces the geometry and coverage Chrome's Skia computes and uses tiny-skia 0.12 only to composite (its raster pipeline, pattern shader and anti-aliased hairline). Ported from Skia at `chrome/m153` (`f8b66b7597c4cc859d3ed190e9c6872241e6721c`), in Skia's `f32` and fixed-point arithmetic:

| Module | Skia and Blink sources | What it decides |
|---|---|---|
| `edges.rs` | Blink `canvas_path.cc` (`arc`, `CanonicalizeAngle`, `AdjustEndAngle`), `path_builder.cc` (`AddEllipse`); `SkPathBuilder::arcTo`, `SkConic::BuildUnitArc`; `SkGeometry.cpp` | Arcs as conics (a whole turn as two half turns); a path that is one filled `arc()` drawn as `drawArc`'s oval, which starts at angle 0; conics to quadratics within 1/4 px; quadratics and cubics cut where they turn |
| `aaa.rs` | `SkScan_AntiPath.cpp`, `SkScan_AAAPath.cpp`, `SkAnalyticEdge.cpp`, `SkEdgeBuilder.cpp`, `SkEdgeClipper.cpp`, `SkLineClipper.cpp`, `SkPathPriv.cpp`, `SkBlitter.cpp`, `SkScan_Antihair.cpp` | Path bounds rounded out and pinned to `±(2^31 − 1) >> 2` (`safeRoundOut`), so coordinates as large as 1e30 still draw, and a path with any non-finite point is dropped (`SkRect::setBoundsCheck`); analytic coverage: curves cut into `2^shift` lines with y snapped to quarter pixels, the convex and general scan-line walkers, the trapezoid alpha of each strip, the mask and run-length blitters and their alpha snapping, `blitFatAntiRect` for small rectangles, `AntiFillRect` for axis-aligned images |
| `stroke.rs` | `SkStroke.cpp`, `SkStrokerPriv.cpp` | Stroke outlines: caps, joins, curve offsets by quadratics, `strokeRect` for closed rectangles; round caps, joins and arcs stay conics; roots are pinned as `SkTPin` does (a NaN becomes the low limit), so a cubic in line with control points at 1e20 strokes as a line to its end |
| `dash.rs` | `SkDashPath.cpp`, `SkDashPathEffect.cpp`, `SkContourMeasure.cpp` | Dashes measured along lines, quadratics, conics and cubics, for hairlines too; butt-capped straight lines dashed straight into rectangles; the cull to the clip; past 1,000,000 dashes the filter gives up and the stroke is drawn undashed (a butt-capped line, already turned into a fill, draws nothing), as `FillPathWithPaint` does |
| `hairline.rs` | `SkScan_Hairline.cpp` (`hair_path`, `extend_pts`, `is_next_contour_closed`, `hair_quad`, `hair_cubic`) | A hairline with a curve whose coordinates are past `sqrt(f32::MAX)` walked as `hair_path` walks it and handed to tiny-skia as the lines Skia draws: tiny-skia's hairliner tests `x * y` for finiteness, which such a curve fails (a debug assertion, and cubic points dropped) where Skia tests each coordinate. Round and square caps extend only a contour's ends and never a closed contour's segments; a curve with an evaluated point that is not finite is skipped alone, and the rest of its contour, the closing line to the contour's first point included, still draws. Other hairlines go to tiny-skia's port of the same hairliner, and a hairline with a non-finite point is dropped |

Before any path is drawn (a fill, a stroke's outline or a hairline), its device-space bounds, control points included, are checked as `SkDraw::drawDevPath` checks them (`SkPathPriv::TooBigForMath`): a coordinate past a quarter of the `f32` range (2^126, about 8.5e37) draws nothing. Chrome 153 draws a line to 8.5070587e37 and nothing past it, for fills, strokes and hairlines alike; clip paths are not checked.

Clips follow `SkRasterClip`: a rectangle within 1/8 px of whole pixels under a scale-translate matrix stays a whole-pixel region, anything else becomes an anti-aliased clip bounded by its non-zero pixels, and draws under an anti-aliased clip use the run-length blitters as `SkAAClipBlitter` forces. Images follow Blink's `ShouldDrawImageAntialiased`: axis-aligned images smaller than a device pixel in either direction are anti-aliased, other axis-aligned images are rounded to whole pixels, rotated ones are filled as paths. `fillRect` follows `SkDraw::drawRect`: `AntiFillRect` under a matrix that keeps rectangles rectangles, the rectangle's path otherwise.

Smoothed images are sampled as Chrome's software canvas samples them (`bilerp.rs`, Skia's bitmap sampler `SkBitmapProcState`): the device pixel centres mapped through the inverse matrix in `f32`, as 32.32 fixed-point positions stepped along each span of equal coverage, split into two clamped texels and a 4-bit weight, and blended with integer weights (`Filter_32_opaque`), so a scaled image shows Chrome's 1/16 steps; an integer translation samples unfiltered. An SVG image goes through `svg.rs`: usvg's tree as fills and strokes for the port's own scan conversion and stroker (quarter circles back as arcs and plain rectangles as `drawRect`, as Blink draws `<circle>` and `<rect>`), or rendered by resvg when it uses what the display list cannot say (gradients, patterns, group opacity, masks, filters, embedded images).

Twenty-nine display lists in `crates/excali-raster/tests/fixtures/display-lists/` exercise fills, `fillRect`, fill rules, curves, arcs, `roundRect`, the path rules, stroke widths, caps, joins, dashes, opacity, colours, transforms, clips, the device pixel ratio, images, huge coordinates (among them whole dashed strokes and hairlines of cubics with control points at 1e20 and 1e30, hairlines with a skipped cubic at ±8e37, and paths past Skia's quarter-range limit) and dash lists past the dash limit, the port's own rough.js output for four Excalidraw shapes, image files of every format Chrome and the port both decode (`images-decoded`, `images-svg`), image elements (`image-elements`, `image-elements-svg`), where Chrome replays upstream's own recorded `renderElement` calls with its own decoders and upstream's placeholder SVGs while the port renders its display list, and `render_static_scene`'s output with image placeholders and link icons named by their built-in ids (`static-scene-images`), which the raster backend resolves itself and Chrome loads from upstream's data URLs. `scripts/fixtures/raster-references.sh` draws each on a real canvas in headless Chrome, which calls the canvas directly and shares no code with the port, and keeps the PNGs; `tests/fixtures.rs` compares the port with them through `excali_raster::diff` under each fixture's tolerance. No fixture pixel is more than 5 levels from Chrome 153 but for eight on the edge of a rotated placeholder, where Chrome's clip of an SVG image to its destination differs from the canvas's clip (up to 17 levels); every fixture allows 8 levels, and `image-elements` 16 pixels past them. CI checks the port against the committed references in the workspace tests and against the runner's Chrome in the `raster-chrome` job, which runs on macOS arm64 like the references: Linux x64 Chrome 153 samples rotated PNG draws differently at their edges.
